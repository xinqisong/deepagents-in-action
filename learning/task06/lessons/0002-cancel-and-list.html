取消一个任务，不等于只看一个状态

本课的唯一目标：你能区分 check_async_task 和 list_async_tasks，并能记录状态来源，而不是只记录状态文字。

先建立知识：两个查询工具

工具范围当前版本的观察重点
check_async_task一个指定的 task读取这个 task 对应的服务端 run；成功时再取回 thread 结果
list_async_tasks所有被 supervisor 跟踪的 task汇总任务；非终态通常读取实时状态，终态可能直接使用 supervisor 缓存
cancel_async_task一个指定的 task请求停止，并先把任务跟踪记录写成 cancelled
关键原则：查询范围不同，状态来源也可能不同。check 更接近某个具体 run；list 更像任务看板。看到不同结果时，先记录 task ID、thread ID、run ID 和工具名称。

本地版本的取消观察模型

cancel_async_task
        │
        ├─ 取消工具确认：cancelled
        │
        ├─ check_async_task
        │      └─ 重新读取服务端 run.status
        │             └─ 可能观察到 interrupted
        │
        └─ list_async_tasks
               └─ 对终态可能使用 supervisor 缓存

LangSmith tracing 另有自己的观测记录：
它描述某条执行过程如何结束，不能直接替代任务看板状态。

这不是要求你预先猜出“最后一定是什么”。实验的目标是学会把每个结果和它的来源绑定起来。

实验步骤

  1. 确认 Agent Server 正在运行：uv run langgraph dev --n-jobs-per-worker 4。
  2. 另开终端运行：uv run python cancel_list_demo.py。
  3. 记录启动后返回的两个完整 task ID；不要截断。
  4. 记录取消前的 list_async_tasks 结果。
  5. 记录取消工具返回的状态，再记录后续 check_async_task 和 list_async_tasks 的状态。
  6. 等待没有被取消的任务完成，确认它是否仍能独立进入 success。

完成标准

  • 能说明 check 是单任务查询，list 是任务总览。
  • 能指出取消任务和未取消任务的 task ID 不同，且未取消任务仍可独立完成。
  • 能解释同一个任务出现 cancelled 与 interrupted 时，下一步应先检查状态来源。
