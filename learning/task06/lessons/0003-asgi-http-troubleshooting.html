先判断任务连到了哪个 Agent 服务

本课的唯一目标：你能从 graph_id、url 和 worker 配置入手，解释一个异步任务为什么“找不到、没进展或调用方式不对”。

1. graph_id 是服务注册名，不是随便起的名字

本地 langgraph.json 把两个图注册为 supervisor 和 researcher。因此 supervisor 中的 AsyncSubAgent(graph_id="researcher") 必须逐字匹配这个注册键。

langgraph.json
  graphs
    supervisor  → ./graphs/supervisor.py:graph
    researcher  → ./graphs/researcher.py:graph

supervisor.py
  AsyncSubAgent(graph_id="researcher")
排障顺序：先检查 graph 是否注册，再检查 graph_id 是否完全匹配，最后才检查模型、鉴权和并发。名称错误时，任务可能还没真正进入 researcher。

2. url 决定传输边界

配置调用方式适合场景
不填写 url同一 Agent Server 内的 ASGI transport本地单服务实验，supervisor 和 researcher 一起注册
填写 url通过 HTTP 调用远程 Agent Protocol 服务拆分部署、独立扩缩容、额外鉴权
填写 headers给 HTTP 请求附加自定义头远程自托管服务的鉴权或租户信息

因此，“把 url 写成 http://127.0.0.1:2024”不是 ASGI，而是让 supervisor 通过 HTTP 访问本地 Agent Server。两种方式都可能可用，但排障时必须知道自己测试的是哪一种。

3. 为什么本地 ASGI 仍要求异步父入口

这里的异步指的是 Agent Protocol 后台任务生命周期，不等于“所有 Python 代码都必须手写 async def”。不过当前本地版本的 AsyncSubAgent 在省略 url 时使用异步 ASGI transport，所以父图应通过异步入口运行，例如 ainvoke 或异步流式入口。

4. worker 槽位是容量，不是任务数量

--n-jobs-per-worker 4

一个 supervisor run       ≈ 占用一个执行槽位
两个后台 researcher runs  ≈ 还需要额外槽位
槽位不足                  → 排队、长时间 running 或没有实质进展

这不是状态机错误，而是容量问题。先用一个 supervisor 加一个 researcher 验证链路，再逐步增加并发；不要一开始同时改变模型、传输方式和 worker 数量。

5. 本次练习：只做无破坏核对

  1. 打开 langgraph.json，确认 supervisor 和 researcher 都已注册。
  2. 打开 graphs/supervisor.py，确认 graph_id="researcher"。
  3. 确认当前配置没有填写 url，因此本章主实验走同部署 ASGI。
  4. 确认启动命令包含 --n-jobs-per-worker 4。
  5. 暂时不要改配置；把“配置事实”和“你推测的原因”分开记录。

完成标准

  • 能解释 graph_id 为什么必须匹配 langgraph.json。
  • 能区分不写 url 的 ASGI 和填写 url 的 HTTP。
  • 遇到任务长期 running 时，会先检查 worker 容量，而不是立即修改业务代码。
