Skill 不是一个更大的 Tool

本课只有一个目标：你能解释一个 Skill 为什么要拆成“元数据、指令、资源”三层，并能把一个需求放进 Skill、Memory 或 Tool 之一。

从 task06 接过来的问题

task06 让你看到：异步子 Agent 解决的是“长任务如何被启动和管理”。但后台研究 Agent 仍然需要知道“研究时先搜什么、如何核对来源、用什么格式交付”。如果每次都把这套流程写进用户提示词，流程就无法稳定复用；如果把所有细节永久塞进系统提示词，又会浪费上下文。

Skill 的三层模型

Agent 启动
  └─ Level 1：name + description
       “我有哪些能力？什么时候可能用到？”

任务匹配
  └─ Level 2：读取 SKILL.md 正文
       “这类任务具体按什么步骤做？”

执行需要
  └─ Level 3：读取 references / assets / scripts
       “这一步需要哪份细节、模板或代码？”
关键洞察：渐进式披露不是把文件分层存放这么简单，而是把“发现能力”和“消耗详细上下文”分开。启动时只让 Agent 看摘要；真正匹配后才读取剧本；执行遇到需要时才加载资源。

和 Tool、Memory 怎么分

如果你要表达的是……优先考虑
“搜索一次”“读一个文件”“调用一次 API”Tool
“每次对话都必须遵守的项目规范”Memory
“遇到报告核验时，按三步检查并使用模板”Skill

现在请先回忆，不要查资料

  1. 如果启动时有 30 个 Skill，为什么不把 30 份正文全部放进系统提示词？
  2. 用户说“帮我按团队规范审查这份 PR”，Agent 最早需要看到 Skill 的哪一部分？之后还要读取哪一部分？
  3. “调用 GitHub API 获取 PR diff”与“审查 PR 时先看 diff、再检查测试、最后按模板输出”分别更像 Tool 还是 Skill？为什么？

请直接在聊天里回答，尽量不用原词堆砌。你的回答会决定下一课是先做目录实验，还是先补一块概念。

参考答案（答完再打开）
  1. 因为大部分 Skill 与当前任务无关；只加载元数据能减少启动上下文，匹配后再加载正文。
  2. 先看 name 和 description 做发现/匹配；匹配后读取 SKILL.md 正文，再按需读取 references、assets 或 scripts。
  3. 调用 GitHub API 是 Tool；“审查时如何组合多个动作并按规范交付”是 Skill。Skill 不替代 Tool，而是指导 Tool 的组合。

完成标准

  • 不用看资料，能说出三层分别解决“发现、执行、细节”中的哪一个问题。
  • 能给出一个真实例子，说明 Skill 如何编排多个 Tool。
  • 能指出“把所有团队规范都做成 Skill”也不合理：始终相关的内容更适合 Memory。
